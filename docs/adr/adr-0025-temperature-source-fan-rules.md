# ADR-0025：按温度来源配置风扇温控规则

- Status：accepted
- Kind：architecture
- Date：2026-10-29
- Supersedes：none
- Implements：#330
- 相关：#470、#471、#332、#334、#473、#474、#475、#478

## 背景

Covio 的风扇曲线已经支持每风扇多点和硬件范围限制。现有控制温度来自用户选择的全部 SMC 传感器。Covio 取这些传感器的最大值，再从一个曲线生成全部风扇目标。

该模型不能表达按 CPU、GPU 或电池分别配置温控规则的需求。电池正常温度也会低于现有曲线下限 `40°C`，因此 `32°C` 和 `34°C` 阈值无法保存。

Research #471 验证了当前 Mac 可以读取三类温度来源：

- CPU：`TCMz`、`TCMb`、`Tp*`、`TC*`、`Te*` 等键。
- Apple Silicon GPU：`Tg*` 键。
- 电池：`TB0T` 至 `TB3T` 键。

Research #471 还确认现有 root helper 可以复用。风扇写入、租约、恢复和控制循环已经存在。缺口是温度来源分组、按来源配置的阈值和百分比目标。

用户提出的 `32°C` 和 `34°C` 电池阈值有效。用户提出的 5 分钟检查周期不能作为安全温控周期。Covio 当前控制循环为 1 秒，MacFanControl 的采样循环为 1.5 秒。

## 决策

1. 增加 `CPU`、`GPU` 和 `battery` 三个温度来源。
2. `battery` 只表示电池温度来源。电源来源仍使用独立概念，不能与温度来源共用枚举。
3. 每个来源由多个 SMC 键组成。Covio 在初始化时发现实际存在的键，并缓存键表。
4. CPU 来源包含 `TCMz`、`TCMb`、`Tp*`、`TC\d\d`，以及机型对应的 `Te*`、`Tf*` 键。
5. Apple Silicon 的 GPU 来源包含 `Tg*` 键。
6. Intel 的 GPU 来源包含 `TG0D`、`TG0H`、`TG0P` 等有效 GPU 键。
7. 电池来源包含 `TB0T`、`TB1T`、`TB2T`、`TB3T`。Covio 只使用实际存在的键。
8. 每个来源的当前温度是该来源全部有效读数的最大值。
9. 未识别或未分组的 SMC 键继续由现有单传感器选择入口控制，不自动加入三个来源。
10. 每个来源保存一组温度控制点。每个控制点包含摄氏度和风扇百分比。
11. 控制点按温度升序排列。相邻控制点至少相差 `2°C`。
12. 相邻控制点之间使用线性插值。第一个点之前使用第一个点的百分比，最后一个点之后使用最后一个点的百分比。
13. 风扇百分比范围为 `0%` 到 `100%`。每台风扇按 `Mn + (Mx - Mn) × 百分比` 换算 RPM，并夹在 `Mn` 和 `Mx` 之间。
14. 每个已启用来源分别计算每台风扇的请求百分比。Covio 对每台风扇取这些请求的最大值。
15. 不按“温度最高的来源”选择来源。CPU、GPU 和电池的温度范围不同，必须比较转换后的风扇请求。
16. 启用来源存在控制点时，来源规则优先于现有 `selectedSensorKeys` 两点或多点 RPM 曲线。
17. 没有来源规则时，保留现有 `selectedSensorKeys` 和每风扇 RPM 曲线行为。
18. 温度读取失败时不得使用 `0°C` 或任何替代温度。
19. 所有已启用来源连续 3 次没有有效读数时，helper 恢复系统风扇控制。
20. 风扇控制循环固定为 1 秒。该值不进入用户配置，不能设置为 5 分钟。
21. 每个来源保留 `1.5°C` 回滞。温度上升立即生效，温度下降不超过回滞值时保持上一控制温度。
22. UI 显示每个已启用来源的当前温度、有效性、控制点和计算出的风扇百分比。
23. 多来源同时生效时，UI 显示每台风扇的最终合并目标，不把合并结果归因于单一来源。
24. 现有配置无需重写。来源规则为空时继续读取原配置。

## 后果

### 正面

- 用户可以为电池设置 `32°C`、`34°C` 等低温阈值。
- CPU、GPU 和电池可以使用各自的温度范围。
- 每台风扇按自己的硬件范围接收百分比目标。
- 多来源规则采用保守合并，不会因为某个来源温度较低而降低另一个来源请求的风扇转速。
- 旧配置和现有单传感器控制继续可用。

### 负面

- 配置模型增加来源规则、控制点和百分比字段。
- helper 请求和状态回复需要携带来源结果。
- UI 需要增加来源启用、控制点编辑和合并状态。
- 不同芯片代的 SMC 键映射需要测试和持续维护。
- 来源规则与现有 RPM 曲线同时存在时，需要明确迁移和优先级提示。

### 风险

- SMC 键会随芯片代际变化。缓解：动态发现实际键，保留未知键入口，并用真机测试固定机型矩阵。
- `TG*` 与 `Tg*` 可能表示不同来源。缓解：按硬件代际选择键族，不按大小写前缀跨平台混用。
- 多来源百分比合并可能产生较高噪音。缓解：保留 1.5°C 回滞，并在 UI 显示每个来源的请求和最终目标。
- 5 分钟采样可能造成温度保护延迟。缓解：禁止配置控制周期，固定为 1 秒。
- 来源配置与 #334 的电源来源曲线可能混淆。缓解：使用独立类型和命名，并在文档中分别解释。

## 备选方案

### 备选 1：继续使用全部已选传感器取最大值

未采纳。该方案不能为 CPU、GPU 和电池设置独立阈值，也不能显示哪个来源产生了风扇请求。

### 备选 2：选择当前温度最高的来源

未采纳。CPU、GPU 和电池的正常温度范围不同。直接比较温度会偏向 CPU，不能反映各来源的温控策略。

### 备选 3：所有来源使用绝对 RPM 控制点

未采纳。不同风扇的 `Mn` 和 `Mx` 不同。绝对 RPM 不能表达用户要求的 `30%` 和 `50%`，也不能保持多风扇同步位置。

### 备选 4：允许 5 分钟控制周期

未采纳。负载变化可能在 5 分钟内产生新的热输入。延迟响应会增加温度越界风险。5 分钟只能用于通知聚合或长时间趋势统计。
