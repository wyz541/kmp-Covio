# 结论与限制

> 本文件承载结论摘要、决策因素、决策表、限制和未决项。

## 1. 结论摘要

跨设备发现与受控操作条件可行。

结论等级是 `conditional-go`。

首版采用以下组合。

1. 局域网发现使用 mDNS。
2. 手动地址始终可用。
3. 公网使用用户自管的 Tailscale/WireGuard。
4. 传输使用 TLS 1.3 上的 WebSocket。
5. 应用协议使用 JSON-RPC 2.0 语义。
6. 身份使用设备证书和双向 TLS。
7. 授权按能力拆分。
8. 自建中继推迟。

条件是先完成 Windows 宿主、macOS 服务端、配对和只读状态。写操作必须逐项通过能力验收。

## 2. 决策因素

### 2.1 主要因素

**F1：Windows 作为系统客户端更合适。**
Windows 只发起出站连接。这样不要求标准用户开放入站防火墙。

**F2：Tailscale 能解决公网可达性，但不能替代应用授权。**
Tailscale 提供 WireGuard 数据面、NAT 穿透、MagicDNS 和网络 ACL。Covio 仍要识别用户和设备。

**F3：自建中继成本超出首版收益。**
中继需要服务器、认证、限速、滥用防护和隐私说明。首版没有账号体系。

**F4：手动地址必须保留。**
mDNS、企业网络隔离和防火墙都可能阻断发现。手动地址是必要恢复路径。

**F5：现有 helper 不能直接暴露。**
现有 Unix 域 socket 只服务本机。网络层需要白名单能力和新的授权边界。

**F6：写操作必须返回观察结果。**
充电、亮度、睡眠和风扇受硬件与系统策略影响。请求成功不等于状态已经改变。

### 2.2 次要因素

**F7：SSDP 不适合本需求。**
SSDP 面向 UPnP，不能解决认证和公网问题。

**F8：协议需要中继适配点。**
首版不实现中继。消息层仍应分离身份、传输和路由。

**F9：能力状态是产品状态。**
没有电池、没有风扇、没有权限或 helper 未安装都是正常结果。界面必须显示原因。

## 3. 决策表

| 决策 | 选择 | 原因 | 备选路径 |
| --- | --- | --- | --- |
| 发现 | mDNS 加手动地址 | 标准、低配置、可恢复 | SSDP，未采用 |
| 公网 | Tailscale/WireGuard | 无需 Covio 自建服务器 | 自建中继，后续 |
| 连接方向 | Windows 连 macOS | 避开 Windows 入站限制 | 双向监听，不采用 |
| 传输 | WebSocket over TLS 1.3 | 双向消息、成熟标准 | 原始 TCP，未采用 |
| 协议 | JSON-RPC 2.0 语义 | 请求、响应、错误结构明确 | 私有 RPC，风险较高 |
| 身份 | 设备证书和公钥指纹 | 不依赖 IP 和主机名 | 仅 Tailscale 身份，不足 |
| 配对 | 高熵 URI 或二维码 | 6 位短码熵不足 | 只用 6 位短码，不采用 |
| 授权 | 按能力 | 最小权限 | 设备全权限，不采用 |
| 撤销 | 删除证书并关闭会话 | 立即生效 | 只从列表移除，不足 |
| 首版写能力 | 无；先只读 | 降低安全风险 | 同时上线全部写操作 |
| 风扇 | 依赖 #313 和 20 秒租约 | 本机安全边界 | 远程无限期接管，不采用 |
| 中继 | 后续版本 | 运维和隐私成本高 | 首版自建，规模过大 |

## 4. 逻辑证据链

### 4.1 观察一：mDNS 是局域网候选标准

观察：RFC 6762 定义无中心服务器的本地链路名称查询。
观察：RFC 6763 定义 DNS-SD 服务发现。
推论：mDNS 可以作为局域网主路径。
置信度：高。

### 4.2 观察二：Windows 标准用户不能创建入站允许规则

观察：Microsoft 文档说明普通用户触发防火墙提示时，系统创建阻止规则。
观察：出站默认允许。
推论：Windows 应只发起连接。
置信度：高。

### 4.3 观察三：Tailscale 提供覆盖网络

观察：Tailscale 使用 WireGuard 数据面。
观察：Tailscale 提供 NAT 穿透、MagicDNS 和 ACL。
推论：Tailscale 可以覆盖首版公网路径。
限制：用户必须安装并登录。
置信度：高。

### 4.4 观察四：应用仍需要自己的身份

观察：Tailscale ACL 是网络层控制。
观察：设备可能加入多个 tailnet 或共享设备。
推论：Covio 必须验证设备证书和能力授权。
置信度：高。

### 4.5 观察五：写能力尚不齐

观察：睡眠控制已有。
观察：充电上限由 #137 推进。
观察：风扇控制由 #313 推进。
观察：亮度控制尚无。
推论：Feature 必须按能力分批交付。
置信度：高。

## 5. 限制

1. 没有完成 Windows 与 macOS 双机实验。
2. mDNS 在企业网络和 VPN 中的行为未验证。
3. Tailscale 依赖用户安装和登录。
4. Tailscale ACL 默认允许全部设备。用户必须自行收紧。
5. 自建中继没有设计。
6. Ktor macOS framework 尚未实测。
7. 配对 UX 和二维码格式尚未冻结。
8. 锁屏时的本机确认策略尚未决定。
9. 远程风扇控制存在硬件和安全风险。
10. 远程睡眠可能造成未保存数据丢失。

## 6. 未决项

1. 配对二维码是否包含局域网地址、Tailscale 名称或两者。
2. 证书使用系统证书库还是应用私有文件。
3. 设备身份密钥的备份和恢复。
4. 是否支持一台 Windows 连接多台 macOS。
5. 是否支持 macOS 主动连接 Windows。
6. 远程写操作的二次确认策略。
7. Tailscale 不可用时的中继迁移时间。
8. 自建中继的隐私与合规范围。
9. 审计日志保留时间和导出方式。
10. 跨版本协议兼容窗口。
