## 结论摘要

`Qwen3-VL-2B-Instruct` 是当前最合适的单模型方案。
它能覆盖文本、代码、图片和扫描 PDF。
模型许可证是 Apache-2.0。
GGUF 运行包约 1.5 GB。
MLX 4 bit 模型约 1.8 GB。

主运行时应采用 MLX Swift。
备选运行时是 llama.cpp。
首版必须使用预览、确定性校验和原子重命名。

本结论不是无条件产品化结论。
MLX Swift 已通过官方 Xcode 示例构建并在本机运行。
条件见本文的未决项。

## 主要决策因素

### 1. 单模型覆盖范围更大

`Qwen3-VL-2B-Instruct` 同时支持文本和图像输入。
模型卡列出 100 多种语言、32 种 OCR 语言和长上下文能力。
本机测试完成了中文文本、Swift 代码、图片和扫描 PDF 页面。
证据：`E-11`、`E-13`、`E-14`、`E-15`、`E-16`。

### 2. 包体积和内存可接受

GGUF 文件为 1,107,409,952 字节。
视觉投影器为 445,053,216 字节。
合计约 1.5 GB。
GGUF 文本运行峰值约 1.75 GB。
GGUF 图片运行峰值约 2.58 GB。
GGUF PDF 页面运行峰值约 2.85 GB。
MLX 文本和图片运行峰值约 1.94 到 1.99 GB。
证据：`E-12`、`E-13`、`E-15`、`E-16`、`E-25`、`E-26`。

### 3. MLX Swift 更符合目标平台

Covio 只构建 Apple Silicon。
部署目标是 macOS 26。
MLX Swift 提供 `MLXVLM` 和 `MLXGuidedGeneration`。
方案不需要启动本地服务器。
本机文本热生成约 1.19 秒。
本机图片热生成约 1.63 秒。
证据：`E-02`、`E-08`、`E-09`、`E-25`、`E-26`。

### 4. llama.cpp 是更成熟的回退路径

llama.cpp 有预编译 macOS arm64 包。
它原生支持 GGUF 和 `mtmd` 多模态输入。
本机 CLI 已验证模型、图片、内存和离线参数。
证据：`E-09`、`E-10`、`E-13` 至 `E-17`。

### 5. 模型不能直接决定最终文件名

模型自报的日期和语言出现错误。
恶意文件内容可以把标题改为 `OWNED`。
模型自报置信度仍为 `0.95` 或 `1.0`。
证据：`E-13`、`E-18`、`E-19`。

因此模型只生成 `title` 和 `category`。
模板、日期、语言、置信度、字符和长度由确定性代码处理。

## 次要决策因素

1. Vision OCR 应作为扫描件的首选路径。
2. 无文本图片才直接使用 VLM。
3. PDFKit 应作为文本 PDF 的首选路径。
4. 模型输出应使用 JSON Schema 或等价引导生成。
5. 应用应在后台预热 Vision 和模型。
6. 批量处理应先完成全量预览。
7. 文件名冲突应追加编号，不应覆盖。
8. 撤销记录应在重命名前写入。
9. 未知或低可信文件应保留原名。
10. 首版应串行处理文件。

## 决策表

| 决策 | 结果 | 原因 |
| --- | --- | --- |
| 模型 | `Qwen3-VL-2B-Instruct` | 单模型覆盖文本、代码、图片和扫描 PDF |
| 权重格式 | MLX 4 bit 为主 | 与主运行时一致 |
| 备选权重格式 | GGUF Q4_K_M 加 Q8_0 mmproj | 已在本机 CLI 验证 |
| 主运行时 | MLX Swift | 原生 Swift、VLM 和引导生成 |
| 备选运行时 | llama.cpp | 成熟、预编译、多模态 |
| 文件提取 | PDFKit、Vision、FileHandle、UTType | 全部本机运行 |
| 模型输出 | 只返回标题和类别 | 其他字段不可靠 |
| 最终名称 | 模板和校验器生成 | 可测试、可限制 |
| 应用方式 | 预览后确认 | 限制提示注入和误改名 |
| 冲突处理 | 追加编号，禁止覆盖 | 避免数据丢失 |
| 撤销 | 重命名前写计划 | 支持恢复 |
| 外部 daemon | 不采用 | 破坏内置和离线体验 |
| 远程模型 | 禁止 | 违反需求 |

## 不采用方案

### Ollama 作为内置运行时

拒绝原因：

1. 需要单独安装或维护守护进程。
2. 进程生命周期和端口冲突增加复杂度。
3. 产物不再是单一菜单栏应用。

### 远程兼容接口

拒绝原因：

1. 违反离线要求。
2. 文件内容可能离开本机。
3. 模型质量和隐私承诺不稳定。

### 文本模型加 OCR 双模型

拒绝原因：

1. 无文字图片无法获得语义。
2. 模型包和内存总和更高。
3. 两套模型会扩大许可证和升级范围。

### 模型直接输出完整文件名

拒绝原因：

1. 无法可靠执行字符、长度和扩展名约束。
2. 提示注入会直接污染路径候选。
3. 模板变化需要重新训练或重写提示。

### 无预览自动改名

拒绝原因：

1. 小模型会误判日期和语言。
2. 文件内容可以注入错误标题。
3. 用户无法在写入前发现批量错误。

## 系统限制

1. 扫描 PDF 的 OCR 质量依赖语言、清晰度和版面。
2. Vision OCR 首次调用可能触发系统模型加载。
3. PDF 页面直接交给 VLM 的耗时明显高于 OCR。
4. 小模型对代码的摘要可能只复述类型名。
5. 小模型不能提供可信置信度。
6. 模型输入需要截断，长文档可能丢失上下文。
7. 图像 token 越多，编码时间越长。
8. macOS 只覆盖 Apple Silicon。

## 产品限制

1. 首版只处理本地普通文件。
2. 首版只重命名，不移动目录。
3. 首版不支持目录、符号链接和跨卷。
4. 首版默认逐文件处理。
5. 首版模型只生成标题和类别。
6. 首版必须显示预览。
7. 首版必须提供撤销。
8. 首版不承诺所有图片都能识别。
9. 首版不承诺所有代码文件都能得到描述性名称。

## 未决项

1. 把 MLX Swift 接入 Covio Xcode 工程。
2. 验证直接 `swift build` 的兼容路径，或固定使用 Xcode 构建。
3. 在 8 GB Mac 上验证峰值内存。
4. 验证模型资产的签名和分发方式。
5. 验证 App Sandbox 与 hardened runtime 的后续方案。
6. 验证 APFS 大小写不敏感目录的原子重命名。
7. 建立正式 12 样本验收集。
8. 验证复杂 PDF、表格和手写文本。
9. 验证批量重命名的部分失败恢复。
10. 评审 Apache-2.0 模型分发所需的 NOTICE。
11. 决定模型随应用内置，还是首次安装包内选择。
12. 将 `decision: pending` 回填到研究 issue。
