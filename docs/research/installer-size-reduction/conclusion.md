## 结论摘要

Covio 的全局最优模型交付方案是：

1. 默认 DMG 只包含 app。
2. 模型在用户确认后按需下载。
3. 模型从固定 revision 下载，并按 app 内 manifest 校验。
4. 下载完成后，模型保存在 app bundle 外。
5. app 更新复用未变化的模型。
6. 需要无网络安装的用户使用可选离线整包。

该方案把默认首次下载从约 `1.54 GB` 降到目标 `50 MB` 以下。
实测默认 DMG 为 `13,218,304` bytes。
实测离线 DMG 为 `1,540,934,144` bytes。
该方案不缩小模型安装后的磁盘占用。
模型质量和 MLX 运行时保持不变。

## 主要决策因素

### 1. 模型是唯一主导项

模型目录为 `1,798,035,956` bytes（`E-02`）。
模型占 app 文件总量的 `98.10%`（`E-03`）。
非模型 app 内容为 `34,731,377` bytes（`E-03`）。
因此，继续优化 Swift 或 KMP 二进制不能改变数量级。

### 2. 压缩不能解决问题

完整 DMG 为 `1,538,632,192` bytes（`E-01`）。
UDZO 压缩比约为 `0.832`（`E-04`）。
模型是高熵量化权重，继续换压缩算法只能得到有限收益。
移除模型后的 DMG 为 `10,877,952` bytes（`E-05`）。
完整包是瘦包的约 `141.45` 倍。

### 3. GitHub 已有成熟的按需模型模式

`WhisperKit` 把模型放在 Hugging Face，并在首次使用时下载（`E-09`）。
`swift-transformers` 提供后台下载、缓存、进度和离线检查（`E-11`）。
`mlx-swift-examples` 用 Hub 下载 MLX 模型并缓存（`E-12`）。
Covio 已经内含 `swift-transformers_Hub.bundle`（`E-08`）。

### 4. 现有校验能力可直接复用

Covio 的模型 manifest 已固定 `modelID`、`revision`、文件大小和 SHA-256（`E-06`）。
`LocalModelPackageVerifier` 已拒绝 revision、大小、路径或许可不匹配的模型（`E-08`）。
因此，模型外置不需要降低完整性保护。

### 5. 完全离线安装仍需保留

ADR-0007 当前要求安装后直接离线使用（`E-16`）。
本方案增加默认在线安装。
可选离线整包保留无网络安装能力（`E-17`）。
所以，新方案需要新 ADR，并取代 ADR-0007 的“只能内置”部分。

### 6. GitHub Release 不适合作为全部模型源

4B 模型为 `3,109,729,929` bytes（`E-06`）。
8B 模型为 `5,776,630,909` bytes（`E-06`）。
30B-A3B 模型为 `18,268,088,064` bytes（`E-06`）。
GitHub Release 单文件必须小于 `2 GiB`（`E-18`）。
因此，模型默认源应采用 Hugging Face Hub。
GitHub Releases 继续发布 app、校验和和可选离线整包。

## 次要决策因素

1. 用户主动确认下载，可以避免静默消耗流量。
2. 下载和校验使用暂存目录，可以避免半成品被加载。
3. app 与模型独立更新，可以减少重复下载。
4. 模型目录使用 Application Support，可以避开 app bundle 更新。
5. 固定 revision 可以保持推理结果可复现。
6. 现有导入入口可以承接企业内部分发和手工安装。

## 根因证据链

```text
User reports 1.54 GB DMG
  -> release asset is 1,538,632,192 bytes (E-01)
  -> model is 1,798,035,956 bytes (E-02)
  -> model is 98.10% of app files (E-03)
  -> DMG compression ratio is 0.832 (E-04)
  -> removing model yields a 10,877,952-byte DMG (E-05)
  -> model revision, size and hashes are pinned (E-06)
  -> Covio already verifies and registers imported packages (E-08)
  -> GitHub apps download and cache models on first use (E-09, E-11, E-12)
  -> choose slim app + controlled model download + optional offline bundle
  -> validate V01 through V09
```

| 决策 | 结果 | 原因 | 证据 |
| --- | --- | --- | --- |
| 默认 DMG 是否包含模型 | 否 | 模型占 `98.10%` | `E-02`、`E-03` |

| 模型完整性 | manifest + SHA-256 | 现有能力可复用 | `E-06`、`E-08` |
| 模型位置 | Application Support | app 更新不覆盖模型 | `E-08` |

## 不采用方案

### A：继续内置模型

该方案保留最直接的离线安装。
它也保留约 `1.54 GB` 的默认下载。
每次 app 更新还会重复携带未变化的模型。
未采用原因：默认包体问题没有解决。

### B：只优化压缩和构建

当前 DMG 已使用 UDZO。
完整 DMG 的压缩比约为 `0.832`。
非模型内容仅约 `34.7 MB`。
即使删掉全部非模型内容，DMG 仍接近模型大小。
未采用原因：收益与问题规模不在同一数量级。

### D：引导器下载完整 app

Figma 的 Dynamic Universal App 为多架构发布减少了重复字节。
Covio 只发布 arm64。
引导器下载的完整 app 仍会包含模型。
未采用原因：没有解决模型分发问题，并增加二次启动流程。

### E：外部 Ollama 或模型服务

该方案可以把模型移出发布包。
用户需要安装和维护外部服务。
后台进程、端口、模型迁移和版本兼容会增加故障面。
未采用原因：破坏单 app 安装体验和离线边界。

### F：只换更小模型

GGUF 2B 路线约 `1.5 GB`。
模型体积仍超过 GB 级。
更换模型需要重新验证质量、内存和许可证。
未采用原因：节省有限，并改变产品能力。

### G：只加 Sparkle 差分更新

Sparkle 的 BinaryDelta 可以缩小后续 app 更新包（`E-13`）。
它不能缩小首次安装包。
未采用原因：与本问题的首要目标不一致。

## 系统限制

1. 模型安装后的稳定体积仍约 `1.8 GB`。
2. 默认在线安装需要一次网络连接。
3. 网络中断、代理和地区可用性会影响首次模型下载。
4. 外部模型完整性依赖 manifest，不能依赖 app bundle 签名。
5. app 更新与模型 revision 需要独立管理。
6. 模型首次加载仍有冷启动时间。

## 产品限制

1. 无模型时，文件自动命名和 Agent 不能执行。
2. 监控、剪贴板、工作区等非 AI 功能应继续可用。
3. 模型下载必须由用户确认，不得静默开始。
4. 下载界面的主文案是中文；现有英文本地化同步存在。
5. 可选离线整包继续使用大文件，不能作为默认推荐。
6. 模型质量不因缩减包体而降低。
